## 1. ملخص سريع

مشروع «كوستر الجامعة» هو تطبيق لإدارة ومتابعة حافلات الجامعة، بواجهة عربية RTL، للطلاب والمشرفين. تحوّل من صفحة HTML منفردة إلى مشروع React 18 وVite، مع Supabase للمصادقة والبيانات والوقت الحقيقي، وLeaflet للخرائط، وPWA.

خلال العمل السابق أضيفت تحسينات واجهة وتجربة الطالب، وفصل غرف دردشة الطلاب إلى شباب وبنات مع أدوات إشراف. ثم عولجت مخاطر أمنية بعد طلب المستخدم حماية الأسرار ومنطق التطبيق: أضيف فحص تلقائي يمنع تسرب أسرار الخادم إلى الواجهة، وفُحصت إعدادات Supabase الحية، وفُعّلت RLS على جدول `buses` دون سياسات بناءً على موافقة المستخدم، ثم أُزيلت سياسة قراءة قديمة غير معزولة للغرف وسُحبت صلاحيات RPC قديمة بعد موافقة منفصلة. نُشرت Edge Function للإشعارات، ودُفعت التغييرات إلى GitHub Pages.

## 3. طلب الحماية وما تعنيه «تشفير الكود» هنا

طلب المستخدم أن يعمل الكود بمفتاح سري، ثم أوضح أن الأولوية هي حماية الأسرار ومنطق التطبيق. جرى توضيح أن تشفير JavaScript الذي يعمل داخل المتصفح لا يجعله سرياً فعلياً: المتصفح يحتاج إلى تنزيله وفك تشغيله، ويمكن للمستخدم استخراج الشيفرة أو تحليلها. لذلك عولجت المسألة بنقل الثقة إلى الخادم، وتقييد قاعدة البيانات، ومنع حزم الأسرار في ملفات الواجهة، بدلاً من إخفاء كود React.

مفتاح Supabase من نوع publishable/anon يعد إعداداً عاماً للواجهة وليس كلمة مرور للخادم. حمايته تأتي من RLS والسياسات وRPC التي تتحقق من هوية المستخدم ودوره، لا من محاولة إخفائه داخل GitHub Actions. يمنع منعاً باتاً وضع `service_role` أو مفاتيح VAPID الخاصة في متغيرات `VITE_*` أو حزمة المتصفح.

## 4. أعمال التدقيق والتنفيذ الأمني

### 4.1 جرد الأسرار وحدود الثقة

- جرى فحص تاريخ Git المتاح بحثاً عن أنماط عالية الثقة لمفاتيح خدمة أو مواد مفاتيح خاصة، دون طباعة قيم حساسة.
- لم يعثر الفحص على مؤشرات عالية الثقة لمفاتيح خدمة أو مفاتيح خاصة في 11 نسخة Git التي كانت متاحة للفحص.
- ملف `.env.local` مستثنى من Git؛ جرى فحص أسماء الإعدادات ونوعها دون كشف القيم، وكان يحتوي إعدادات واجهة عامة فقط وفق سجل التدقيق.
- قيمة Supabase publishable في Workflow عامة بطبيعتها، ولا يجب معاملتها كمفتاح service-role.
- لم تُغيّر مفاتيح المشروع أو تُدوّر؛ لم يثبت تسرب مفتاح حقيقي.

### 4.2 فاحص أسرار الواجهة وCI

أضيف `scripts/check-client-secrets.mjs` وسكربت `npm run check:client-secrets`. يفحص ملفات المصدر وملفات البناء، ويسمح فقط بإعدادات Supabase العامة المعروفة، ويرفض أسماء متغيرات Vite غير الموثقة ومؤشرات أسرار الخادم أو مفاتيح PEM/JWT الخاصة. يتجنب طباعة قيمة المطابقة. أضيف تشغيل الفحص إلى Workflow GitHub Pages قبل `npm run build` وبعده.

ملفات مرتبطة:

- `scripts/check-client-secrets.mjs`
- `tests/clientSecrets.test.js`
- `.github/workflows/pages.yml`
- `package.json`

### 4.3 سياسات Supabase الحية وجدول buses

كشف الفحص الحي أن `public.buses` كان لديه RLS معطلاً، مع امتيازات لدوري `anon` و`authenticated`. طلب المستخدم صراحة تفعيل RLS على `buses` فقط وقَبِل حجب الوصول إلى أن يضيف السياسات. نُفذ هذا الإجراء وحده في تلك المرحلة، ولم تُنشأ سياسة تخمينية.

**الحالة الحالية:** RLS مفعّل على `public.buses` ولا توجد سياسات. لذلك الوصول المباشر من التطبيق/الأدوار التي تعتمد على PostgREST سيظل محجوباً حتى يحدد مالك المشروع سياسة قراءة/كتابة مناسبة. لا يشير كود المستودع الذي جرى فحصه إلى استخدام `public.buses` مباشرة، لكن قد توجد مستهلكات خارجية لم يشملها التدقيق.

### 4.4 عزل دردشة الشباب والبنات

كشف التدقيق سياسة قديمة باسم `student_chat_messages_eligible_read` كانت تسمح بقراءة رسائل على أساس الاشتراك دون ربط مجموعة الطالب بالغرفة. طلب المستخدم أولاً عدم حذفها، ثم بعد استكمال التدقيق وافق صراحة على حذفها.

بعد الموافقة:

- حُذفت السياسة القديمة وحدها؛ لم تُحذف أي رسائل.
- تحققنا أن سياسة `student_chat_messages_room_read` بقيت وحدها لقراءة الرسائل وأن شرطها يربط مجموعة الطالب بالغرفة.
- ظل فصل غرفتي الشباب والبنات قائماً، وبقي المشرف قادراً على العمل في الغرفتين وفق مسارات RPC المحددة.

### 4.5 تقليص صلاحيات RPC القديمة

طُبق ترحيل أقل صلاحيات بعد مراجعة توقيعات الدوال الحية:

- سُحبت صلاحيات `EXECUTE` عن RPC الدردشة القديمة غير المحددة بالغرفة، بما فيها إرسال/بلاغ/حذف/قائمة بلاغات، من `PUBLIC` و`anon` و`authenticated`.
- سُحبت صلاحية `anon` من `is_admin()` مع إبقاء وصول المستخدم المسجل اللازم لسياسات RLS الحالية.
- سُحبت صلاحيات الاستدعاء المباشر لـ`handle_new_user()` عن أدوار العميل. فُحص بقاء مشغل Auth `on_auth_user_created` مفعلاً على `auth.users`؛ منع الاستدعاء من API لم يعطل المشغل.
- أبقي وصول `service_role` لأغراض الصيانة كما هو مقصود في الترحيل.
- تحققت صلاحيات الدوال بعد التنفيذ عبر استعلامات كتالوج PostgreSQL و`has_function_privilege` وفق سجل العمل.

الدوال الجديدة المحددة بالغرفة، مثل `chat_room_access` و`send_chat_room_message` و`report_student_chat_room_message`، راجعها التدقيق ووجد فيها تحقق هوية/مجموعة/دور. كما راجع دوال المشرف ورحلات الحافلة والإحصاءات الإجمالية.

### 4.6 Edge Function للإشعارات

استُرجع مصدر Edge Function الحية باسم `bright-task`، وكانت نقطة ضعف المصدر السابق أن الأخطاء قد تكشف تفاصيل داخلية، كما أن استدعاء العميل لم يطابق slug المنشور. أضيف إلى المستودع مصدر قابل للمراجعة في `supabase/functions/bright-task/`، وأصلح استدعاء العميل إلى slug `bright-task`.

التغييرات تشمل:

- تفعيل/الإبقاء على التحقق من JWT (`verify_jwt=true`).
- التحقق داخل الدالة من Bearer token ومن المستخدم الفعلي.
- التحقق من أن ملف المستخدم مشرف نشط على الخادم.
- التحقق من UUID لمعرف الإعلان ونوع الطلب.
- تحديد حجم JSON إلى 8192 بايت ومعالجة تدفق الطلب وإلغاء القراءة عند تجاوز الحد.
- إعادة رسائل خطأ عامة بدلاً من تفاصيل قاعدة البيانات أو Web Push.
- قراءة `SUPABASE_SERVICE_ROLE_KEY` ومفاتيح VAPID من `Deno.env` فقط؛ لم تُضمّن القيم في واجهة React ولم تتغير الأسرار.
- إضافة ملف Deno وإصدارات الاعتماديات المثبتة واختبارات للحالات الأمنية.

نُشرت الدالة في Supabase وأكدت أداة MCP أنها `ACTIVE` بإصدار 5 وبـ`verify_jwt=true`. جرى فحص المصدر محلياً باستخدام Deno. **لم نرسل إشعار Push حقيقياً كاختبار** لأن الدالة قد تبث إلى جميع الاشتراكات النشطة ضمن الجمهور المستهدف؛ يجب أولاً تجهيز جمهور داخلي مضبوط.

### 4.7 إعدادات Auth التي لم تتغير

أبلغ مستشار Supabase أن حماية كلمات المرور المسرّبة عبر HaveIBeenPwned معطلة. لا توفر أدوات MCP المتاحة عملية لتغيير ذلك الإعداد. عند محاولة فتح لوحة المشروع ظهرت صفحة تطلب تسجيل الدخول. طلب المساعد من المستخدم تسجيل الدخول، لكن المستخدم رفض صراحة: «لا اسجل دخول».

**النتيجة:** لم يتم تسجيل دخول المستخدم، ولم يتم تفعيل فحص كلمات المرور المسرّبة، ولم يُغيّر أي إعداد آخر عبر لوحة Auth. يجب احترام هذا القرار وعدم إعادة طلب بيانات الدخول بلا داعٍ. يمكن للمالك لاحقاً تفعيل الخيار بنفسه من لوحة Supabase.

كذلك بقي حد `admin_reset_password` الأدنى ستة أحرف. لم يُرفع الحد، لأن ذلك يحتاج مواءمة بين إعداد Auth وسياسة المشروع وواجهة إعادة تعيين كلمة المرور واختبارها.

## 7. تاريخ القرار والنشر

التسلسل الأبرز للقرارات الأمنية:

1. طلب المستخدم حماية الأسرار ومنطق التطبيق بعد الحديث عن تشفير الكود.
2. وافق على خطة التدقيق والتنفيذ.
3. وافق على تفعيل RLS على `buses` فقط، مع قبول حجب الوصول حتى إضافة السياسات.
4. طلب عدم حذف سياسة الدردشة القديمة في البداية، وطلب إكمال التدقيق.
5. بعد مراجعة نتائج التدقيق، وافق صراحة على حذف السياسة القديمة المحددة ومواصلة التحقق والنشر.

7. رفض المستخدم تسجيل الدخول إلى لوحة Supabase؛ لذلك بقي إعداد كلمات المرور المسرّبة بلا تغيير.
8. نُشر commit التطبيق الأمني `a0ca0d0` ثم commit توثيق الحالة `bd2bc90` إلى `main` في المستودع `coaster-react-vite`، وكلا نشر Pages المرتبطين به نجح وفق السجل. الحالة النهائية `bd2bc90`.

## 8. البنود المفتوحة والأولويات التالية

### مطلوب قرار/تنفيذ من مالك المشروع

1. **سياسات `public.buses`:** تحديد من يحتاج القراءة والكتابة، ثم صياغة أقل صلاحيات واختبار المستهلكات، وبعد موافقة المستخدم تطبيق السياسة. حالياً RLS يصد الوصول المباشر.
2. **حماية كلمات المرور المسرّبة:** يفعّلها المالك بنفسه من Supabase Dashboard؛ لم يسمح المستخدم بالدخول في الجلسة.
3. **كلمة المرور:** مراجعة حد الستة أحرف في `admin_reset_password` ومواءمته مع إعداد Auth وواجهة الإدارة. لا تغيّره قبل تحديد السياسة واختبارات UI/RPC.
4. **اختبار Push حي:** تجهيز مجموعة أجهزة/اشتراكات اختبار داخلية، إرسال إعلان موجه لها، والتحقق من التسليم والسجلات. لا تستخدم إعلاناً عاماً كاختبار.

### صيانة هندسية

5. معالجة تحذير Vite الخاص بالاستيراد الديناميكي والثابت إذا كان فصل حزمة Supabase مطلوباً؛ هذا تحسين أداء وتنظيم وليس ادعاء وجود سر.
6. متابعة تنبيهات GitHub Actions الخاصة بإصدارات Node runner و`ubuntu-latest` وترقية الإصدارات المدعومة بعد اختبارها.
7. توحيد تاريخ migrations الحي والمستودع قبل اعتماد نشر مخطط متكرر.
8. عند إجراء أي تعديل على Supabase، افحص `git status` والفرع والـremote، ثم راجع SQL والمستخدمين المتأثرين، وخذ موافقة مستقلة على أي تغيير إنتاجي عالي الأثر.

- ابدأ من الحالة النهائية `bd2bc90` على فرع `main`، ولا تعِد تنفيذ تغييرات RLS أو نشر Edge Function دون حاجة.
- اقرأ هذا التقرير و`docs/security/assessment.md` قبل أي خطوة جديدة.
